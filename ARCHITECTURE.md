# Концепция торгового бота (Forex + Crypto: Bybit, Binance)

## 0. Итоговые решения по MVP

Зафиксировано на этапе концепции:

- **Первое направление — Forex.** Крипта (Binance/Bybit) подключается позже как второй Data Layer поверх того же ядра.
- **Источник данных для Forex — MetaTrader5** (пересмотрено после MVP: см. §3.1). Изначально основным был выбран iTick (обоснование ниже) — это решение отменено: бесплатный ключ iTick перестал работать на практике (`401 Unauthorized`, требует ручного продления), и провайдер удалён из кода целиком (`tradon.data.itick` больше не существует). yfinance — резерв.
- **Только сигналы.** Автотрейдинг (исполнение ордеров) не входит в MVP — режим "сигнальный", без реальных сделок.
- **Первый интерфейс — CLI.** Используется для тестирования ядра (данные → стратегии → сигналы) до появления GUI/Web.
- **База данных — SQLite по умолчанию** (пересмотрено после MVP: см. §3.5). PostgreSQL остаётся целевым решением для многопользовательских этапов (Web, Этап 4+), доступен через `docker-compose.yml` или VPS — переключение это только смена `DATABASE_URL`, схема и код не меняются.

## 1. Цели и принципы

- **Мультирыночность**: единая логика для Forex и крипты, разные адаптеры данных/исполнения.
- **Поэтапность**: MVP на CLI → GUI → Web → мессенджеры, без переписывания ядра на каждом шаге.
- **Разделение слоёв**: ядро (данные, стратегии, сигналы) не знает, как результат будет показан — CLI/GUI/Web/Telegram лишь подписчики на события ядра.
- **Расширяемость стратегий**: новая стратегия = новый плагin, без изменения ядра.
- **Многозадачность**: параллельный сбор котировок по десяткам инструментов и бирж без блокировок.

## 2. Поэтапный план разработки

### Этап 0 — Концепция и каркас (текущий)
- Финализировать архитектуру, выбрать стек, описать интерфейсы модулей (контракты).
- Определить MVP-набор: 1–2 источника данных, 2–3 инструмента, 1–2 стратегии, вывод в CLI.

### Этап 1 — MVP (Forex, CLI, только сигналы)
- Слой данных: один источник Forex-котировок (MetaTrader5 **или** yfinance для старта — см. раздел 3.1) для 3–5 валютных пар.
- 1–2 простые стратегии (например, пересечение скользящих средних, RSI).
- Генерация сигналов в консоль (`Rich`) + запись в БД.
- Хранилище: **SQLite по умолчанию** (см. §3.5), Postgres опционально; доступ через `SQLAlchemy` (Async) + миграции `Alembic`.
- Конфигурация через YAML/ENV.

### Этап 2 — Мультиисточники и крипта
- Добавление Binance и Bybit API (крипторынок) поверх той же схемы БД — без переделки Data Layer.
- Кеширование и нормализация данных из разных источников в единый формат (OHLCV + метаданные).
- Планировщик задач (сбор данных по расписанию/по вебсокету), базовая многозадачность (asyncio).

### Этап 3 — GUI (десктоп)
- Настольное приложение (просмотр графиков, сигналов, управление стратегиями) поверх того же ядра.
- Возможность включать/выключать стратегии и инструменты через интерфейс.

### Этап 4 — Web
- Web-интерфейс (дашборд, графики, история сигналов) через REST/WebSocket API поверх ядра.
- Многопользовательский доступ (аккаунты, права).

### Этап 5 — Мессенджеры и уведомления
- Telegram/Discord-боты: подписка на сигналы, управление стратегиями командами.
- Push-уведомления о срабатывании сигналов, ошибках подключения к биржам.

### Этап 6 — Продвинутая аналитика и торговля
- Бэктестинг стратегий на истории.
- Автоматическое исполнение ордеров (опционально, с риск-контролем).
- Портфельная аналитика, статистика по стратегиям (winrate, profit factor, drawdown).

> Важно: каждый этап добавляет **новый слой поверх ядра**, а не переделывает предыдущий. Это возможно только если контракты между слоями зафиксированы с самого начала (этап 0).

## 3. Архитектура (модульная, слоистая)

```
┌─────────────────────────────────────────────┐
│  Presentation Layer: CLI / GUI / Web / Bots  │  ← подписчики на события ядра
├─────────────────────────────────────────────┤
│  Notification Layer: Telegram / Discord /... │
├─────────────────────────────────────────────┤
│  Signal Engine  →  Strategy Engine (plugins) │  ← ядро анализа
├─────────────────────────────────────────────┤
│  Risk Management (позиции, стопы, сайзинг)   │
├─────────────────────────────────────────────┤
│  Data Layer (адаптеры + нормализация)        │
│    Yahoo | MetaTrader | Binance | Bybit      │
├─────────────────────────────────────────────┤
│  Database (котировки, сигналы, сделки, лог)  │
├─────────────────────────────────────────────┤
│  Task Scheduler / Async Engine (многозадачн.)│
└─────────────────────────────────────────────┘
```

### 3.1 Data Layer
- Единый интерфейс `DataProvider` с методами `get_ohlcv()`, `subscribe_realtime()`, `get_symbols()`.
- Реализации-адаптеры: `YahooProvider`, `MetaTraderProvider`, `BinanceProvider`, `BybitProvider`.
- Все адаптеры приводят данные к единой модели `Candle(symbol, timeframe, open, high, low, close, volume, timestamp, source)`.

**Источник для Forex — MetaTrader5 (основной), yfinance — резерв.**

> **Обновление после MVP.** Изначально основным источником был выбран
> iTick — обоснование этого выбора оставлено ниже как исторический
> контекст, решение было разумным на момент принятия. На практике
> бесплатный API-ключ iTick перестал работать (`401 Unauthorized`,
> нужно периодически вручную обновлять на itick.org), и поддерживать
> это ради бесплатного тарифа не было смысла — `iTickProvider` и
> `tradon.data.itick` удалены из кода полностью. MetaTrader5 (требует
> запущенный залогиненный терминал на той же машине, связь по local
> IPC, не по сети — отмеченный ниже риск кроссплатформенности
> подтвердился) занял место основного источника для Forex; если
> понадобится источник без десктоп-терминала, нужен новый адаптер,
> реализующий `DataProvider` тем же способом, каким были добавлены
> Binance/Bybit.

Почему изначально выбрали iTick, а не MetaTrader5 (исторический контекст, see выше):
- Обычный REST + WebSocket API (`https://api.itick.org`) — работает с любой ОС, не требует Windows-моста, как MetaTrader5. Это снимает риск кроссплатформенности, который отмечен в разделе 6.
- Есть готовые эндпоинты под форекс: `/forex/quote`, `/forex/tick`, `/forex/kline` (REST) и WebSocket-поток с реал-тайм котировками, тиками и стаканом по основным парам (EUR, GBP, JPY, CHF и др.).
- Бесплатный тариф закрывает MVP: 5 REST-запросов/мин, 1 WebSocket-соединение, до 3 подписок — этого достаточно для 3–5 пар в сигнальном режиме без автотрейдинга.

### 3.2 Strategy Engine
- Интерфейс `Strategy`: принимает поток свечей/индикаторов, возвращает `Signal(symbol, direction, strength, timestamp, reason)`.
- Стратегии — плагины (папки/модули), подключаемые через конфиг, без изменения ядра.
- Библиотека индикаторов отдельно (SMA, EMA, RSI, MACD, Bollinger и т.д.) — переиспользуется разными стратегиями.

### 3.3 Signal Engine
- Агрегирует сигналы от нескольких стратегий/инструментов.
- Фильтрация (например, сигнал подтверждён двумя стратегиями), дедупликация, приоритизация.
- Публикует события через внутреннюю шину (event bus / очередь) для всех подписчиков (CLI, БД, уведомления).

### 3.4 Risk Management
- Расчёт размера позиции, стоп-лосс/тейк-профит по правилам (ATR, % от депозита и т.д.).
- Независим от конкретной стратегии — принимает сигнал и параметры риска.

### 3.5 Database — SQLite по умолчанию, Postgres для многопользовательских этапов

**Пересмотрено после MVP.** Первоначальное решение (см. историю ниже) было — PostgreSQL с первого дня, чтобы не упереться в блокировку записи SQLite при параллельном доступе Data Layer + Signal Engine + Presentation Layer. На практике для текущего этапа (один пользователь, один процесс — CLI или GUI — опрашивает и пишет за раз) это оказалось лишней инфраструктурой: Docker Desktop на Windows поднимает WSL2-виртуалку с заметным потреблением ресурсов, а вынос БД на VPS усложняет запуск (SSH-туннель, firewall) без реальной необходимости на этой стадии.

Текущее решение: **SQLite-файл (`data/tradon.db`) по умолчанию**, с `PRAGMA journal_mode=WAL` и `busy_timeout=5000` на каждом соединении — это снимает конкретно тот риск, из-за которого изначально отказались от SQLite (чтения не блокируются записью; если два процесса всё же пишут одновременно, второй ждёт до 5с вместо мгновенной ошибки "database is locked"). Модели не используют Postgres-специфичные типы (`sa.JSON` вместо `JSONB`, generic `Numeric`/`DateTime(timezone=True)`) — переход на Postgres, когда он реально понадобится (Этап 4, Web, много пользователей одновременно), это смена `DATABASE_URL`, без изменений кода и схемы. PostgreSQL остаётся доступен через `docker-compose.yml` (локально) или на VPS через SSH-туннель — см. README «Database setup».

**Доступ из кода**: `SQLAlchemy` (async, через `aiosqlite`/`asyncpg` — выбирается по `DATABASE_URL`) как единственный слой работы с БД + `Alembic` для миграций схемы (`render_as_batch=True`, чтобы будущие `ALTER` работали и на SQLite).

**Правила схемы, чтобы переключение на Postgres в будущем было бесшовным**:
- Цены и объёмы — `Numeric`, а не `Float` (точность для финансовых расчётов).
- Все временные метки — timezone-aware (`DateTime(timezone=True)`, UTC), а не naive datetime.
- Внешние ключи и индексы на `(symbol, timeframe, timestamp)` для `candles` — таблица будет расти быстрее всех.
- Параметры стратегий — `JSON` (generic, не `JSONB`) — работает на обоих движках без изменений.

**Таблицы (минимальный набор под MVP)**:
  - `instruments` (symbol, market_type, exchange)
  - `candles` (symbol, timeframe, timestamp, OHLCV, source) — индекс по `(symbol, timeframe, timestamp)`
  - `strategies` (name, params `JSON`, enabled)
  - `signals` (strategy_id, symbol, direction, timestamp, strength, status)
  - `trades` (signal_id, entry, exit, size, pnl) — появится на этапе 6, но место в схеме закладываем сразу
  - `users` — для Web/мессенджеров (этапы 3–5)

**Тесты**: для unit-тестов — отдельная SQLite in-memory база или тестовый контейнер Postgres (`testcontainers`) — но это только для CI, не для рабочего режима бота.

### 3.6 Task Scheduler / многозадачность
- `asyncio` как основа: параллельный опрос REST API, приём WebSocket-потоков без блокировки друг друга.
- Очередь задач (например, APScheduler для периодических задач + asyncio для потоковых).
- При росте нагрузки — вынос тяжёлых вычислений (бэктест, индикаторы на больших данных) в отдельные процессы/воркеры (multiprocessing или Celery + Redis).

### 3.7 Presentation Layer
- CLI: `Typer`/`argparse` + `Rich` для форматированного вывода в терминал.
- GUI: `PyQt`/`PySide` (десктоп) — подключается к тому же ядру напрямую или через локальный API.
- Web: `FastAPI` (REST + WebSocket) как бэкенд, любой фронтенд (React/Vue) или встроенные шаблоны.
- Мессенджеры: `aiogram` (Telegram), аналогично для Discord.

Ключевой момент: CLI/GUI/Web/боты **не содержат логики анализа** — они только вызывают API ядра и рендерят результат. Это и даёт "поэтапность" без переписывания.

## 4. Предлагаемый технологический стек (Python)

| Слой | Инструменты |
|---|---|
| Язык | Python 3.11+ (богатая экосистема для трейдинга и асинхронности) |
| Данные: крипто | `ccxt` (универсальный) или нативные `python-binance`, `pybit` |
| Данные: Forex | `MetaTrader5` (local IPC, требует запущенный терминал) — основной; `yfinance` — резерв (iTick удалён, см. §3.1) |
| Асинхронность | `asyncio`, `aiohttp`/`websockets` |
| БД | SQLite (по умолчанию) + `SQLAlchemy` (Async) + `Alembic`; Postgres опционально (Docker/VPS) — см. §3.5 |
| Планировщик | `APScheduler` (простые задачи), позже `Celery` + `Redis`/`RabbitMQ` при масштабировании |
| CLI | `Typer` + `Rich` |
| GUI | `PyQt6`/`PySide6` |
| Web backend | `FastAPI` (REST + WebSocket) |
| Web frontend | React или встроенные Jinja2-шаблоны (проще для старта) |
| Мессенджеры | `aiogram` (Telegram) |
| Конфигурация | `pydantic-settings` + YAML/ENV |
| Тесты | `pytest` |

> Альтернатива: если предпочтение отдаётся .NET/Java/Node.js — архитектура (слои, контракты) остаётся такой же, меняются только конкретные библиотеки. Дайте знать, если стек уже определён — подгоню рекомендации.

## 6. Риски и на что обратить внимание заранее

- **Разные форматы данных** у Yahoo/MetaTrader/Binance/Bybit (таймзоны, точность цены, лимиты запросов) — нормализация в Data Layer критична с первого дня.
- **Rate limits и переподключения** WebSocket у бирж — нужен слой устойчивости (retry, backoff) в Data Layer.
- **MetaTrader5 API работает только на Windows** — если нужна кроссплатформенность, стоит рассмотреть MT-мост через отдельный Windows-сервис или брокеров с REST/FIX API.
- **Автотрейдинг** — юридические и финансовые риски, стоит явно разделить "сигнальный" и "исполнительный" режимы.
